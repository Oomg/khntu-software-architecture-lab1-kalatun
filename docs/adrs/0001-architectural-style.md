# ADR-0001. Вибір архітектурного стилю для ядра системи
[ADR-KhNTU-Ref: 42010-v1.42]

## Статус
Accepted

## Контекст (Context)
Система бронювання квитків розробляється з нуля невеликою командою. Основний архітектурний виклик — забезпечити високу швидкість розробки на старті, зберігши при цьому здатність системи до горизонтального масштабування в майбутньому (під час пікових навантажень на старті продажів топових подій). Пряме створення мікросервісів зараз призведе до невиправданих витрат часу на налаштування інфраструктури.

## Рішення (Decision)
Прийнято рішення використовувати **Модульний моноліт (Modular Monolith)** із застосуванням принципів **Clean Architecture** для ізоляції бізнес-логіки. Усі модулі (Пошук подій, Бронювання, Оплата, Користувачі) знаходяться в єдиному репозиторії та розгортаються разом, але їхній код суворо ізольований один від одного через публічні інтерфейси.

## Розглянуті альтернативи (Alternatives Considered)
* **Класичний моноліт (Layered 3-Tier):** Відхилено. Ризик перетворення коду у «Велику грудку бруду» (Big Ball of Mud) та неможливість безболісно виділити окремі сервіси в майбутньому.
* **Мікросервісна архітектура (Microservices):** Відхилено на даному етапі. Висока мережева затримка, складність розподілених транзакцій та надмірні вимоги до DevOps для початкового запуску.

## Наслідки (Consequences)
* **Позитивні наслідки:** Простіше розробляти, тестувати та розгортати систему; відсутність мережевих затримок між модулями; можливість легкого рефакторингу в мікросервіси згодом.
* **Компроміси (Trade-offs):** Потребує суворого контролю на етапі Code Review, щоб уникнути прямого зв'язування (coupling) модулів та імпорту внутрішніх класів в обхід інтерфейсів.
