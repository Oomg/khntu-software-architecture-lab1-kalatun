# Сценарії якісних атрибутів (Quality Attribute Scenarios)
Документ містить 5 детальних сценаріїв, що описують реакцію системи "Online Ticket Booking & Event Platform" на специфічні події для перевірки досягнення нефункціональних вимог (NFR).

## 1. Performance Efficiency (Продуктивність під час розпродажу)
* **Source (Джерело):** Зареєстрований покупець.
* **Stimulus (Імпульс):** Надсилання HTTP GET запиту на пошук подій та перевірку доступності місць на схемі залу.
* **Environment (Середовище):** Пікове навантаження системи (Peak Load, старт продажів квитків, 1000 RPS).
* **Artifact (Артефакт):** API Gateway, Сервіс Пошуку (Search Service) та База даних.
* **Response (Реакція):** Запит приймається в обробку, система паралельно запитує кеш та БД, після чого повертає актуальний список доступних місць без помилок.
* **Response Measure (Метрика):** Latency p95 <= 142 ms; відсоток успішних відповідей становить 100%.

## 2. Reliability (Відмовостійкість сервісу бронювання)
* **Source (Джерело):** Апаратний або програмний збій (система внутрішнього моніторингу).
* **Stimulus (Імпульс):** Раптове падіння (crash) основного екземпляра сервісу бронювання (Booking Service).
* **Environment (Середовище):** Нормальний режим роботи системи з активними транзакціями (Normal operation).
* **Artifact (Артефакт):** Модуль бронювання, оркестратор контейнерів (Kubernetes) та Load Balancer.
* **Response (Реакція):** Оркестратор виявляє збій через health-check, ізолює несправний вузол і автоматично перенаправляє нові запити на резервний екземпляр сервісу.
* **Response Measure (Метрика):** Час автоматичного перемикання (Failover time) становить ≤ 30 секунд; жодна раніше підтверджена транзакція не втрачається.

## 3. Security (Захист від ботів-перекупників)
* **Source (Джерело):** Зовнішній зловмисник (бот-мережа або скрипт перекупника).
* **Stimulus (Імпульс):** Спроба масового створення замовлень (надходження понад 50 POST-запитів на бронювання за 1 хвилину з однієї IP-адреси).
* **Environment (Середовище):** Відкритий продаж квитків на топову подію (High demand / Under attack).
* **Artifact (Артефакт):** Web Application Firewall (WAF), модуль Rate Limiting та API Gateway.
* **Response (Реакція):** Система ідентифікує аномальну активність, відхиляє наступні запити з кодом `429 Too Many Requests` та тимчасово додає IP-адресу до чорного списку.
* **Response Measure (Метрика):** Блокування IP-адреси застосовується автоматично на 15 хвилин; затримка спрацювання захисту становить ≤ 1 секунди з моменту перевищення ліміту.

## 4. Maintainability (Тестування критичної бізнес-логіки)
* **Source (Джерело):** Backend-розробник.
* **Stimulus (Імпульс):** Внесення змін у алгоритм запобігання подвійному бронюванню місця та відправка коду (git push) до репозиторію.
* **Environment (Середовище):** Середовище розробки та CI/CD (Development / Testing environment).
* **Artifact (Артефакт):** Вихідний код Order Processing Module та CI/CD пайплайн (наприклад, GitHub Actions).
* **Response (Реакція):** Система автоматично запускає набір unit-тестів та статичний аналіз коду для перевірки нової логіки.
* **Response Measure (Метрика):** Покриття коду тестами залишається ≥ 80%; час виконання всього набору тестів у пайплайні становить ≤ 5 хвилин.

## 5. Flexibility (Масштабованість при напливі користувачів)
* **Source (Джерело):** Інфраструктурний моніторинг (DevOps).
* **Stimulus (Імпульс):** Зростання навантаження на CPU сервісу Orders API понад 70% протягом 2 хвилин поспіль.
* **Environment (Середовище):** Раптовий наплив трафіку (наприклад, після анонсу події в соціальних мережах).
* **Artifact (Артефакт):** Orders API Service та група автомасштабування (Auto-scaling group).
* **Response (Реакція):** Система автоматично ініціює запуск додаткових екземплярів сервісу Orders API та реєструє їх у Load Balancer для розподілу трафіку.
* **Response Measure (Метрика):** Нові екземпляри успішно додаються та починають приймати трафік за час ≤ 2 хвилин; середнє навантаження на CPU стабілізується нижче порогу в 70%.
