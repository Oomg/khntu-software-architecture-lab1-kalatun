# ADR-0003. Стратегія автентифікації та безпеки
[ADR-KhNTU-Ref: 42010-v1.42]

## Статус
Accepted

## Контекст (Context)
Система матиме кілька типів користувачів (покупці, адміністратори, організатори). Архітектура має бути готовою до горизонтального масштабування, що ускладнює використання традиційних сесій, збережених у пам'яті конкретного сервера.

## Рішення (Decision)
Прийнято рішення використовувати **Stateless автентифікацію на основі JWT (JSON Web Tokens)** у комбінації зі стандартом **OAuth 2.0 / OpenID Connect**. Для управління ідентифікаціями буде розгорнуто готове рішення (Identity and Access Management), наприклад, Keycloak.

## Розглянуті альтернативи (Alternatives Considered)
* **Stateful Sessions (Cookies у пам'яті сервера):** Відхилено. Це змушує використовувати механізм "sticky sessions" на балансувальнику навантаження, що серйозно обмежує можливості еластичного автомасштабування сервісів.
* **Basic Authentication:** Відхилено через критичну вразливість передачі облікових даних при кожному запиті та незручність управління життєвим циклом токенів.

## Наслідки (Consequences)
* **Позитивні наслідки:** Сервери залишаються stateless (без стану), що дозволяє миттєво додавати нові екземпляри при навантаженні; спрощується інтеграція з мобільними клієнтами.
* **Компроміси (Trade-offs):** Складність механізму відкликання токенів (invalidation). Оскільки JWT дійсний до закінчення терміну дії, для негайного блокування користувача доведеться імплементувати механізм чорних списків (Blacklist) на рівні API Gateway.
