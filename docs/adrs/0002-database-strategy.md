# ADR-0002. Вибір стратегії зберігання даних
[ADR-KhNTU-Ref: 42010-v1.42]

## Статус
Accepted

## Контекст (Context)
Система продажу квитків вимагає суворих транзакційних гарантій (ACID), щоб унеможливити подвійне бронювання одного й того ж місця кількома користувачами одночасно. З іншого боку, система повинна витримувати велику кількість запитів на читання (перегляд афіші та схем залів).

## Рішення (Decision)
Прийнято рішення використовувати **PostgreSQL** як основну реляційну базу даних для збереження транзакційних даних (замовлення, квитки, фінанси), а також **Redis** як in-memory сховище для кешування каталогу подій та тимчасового блокування (distributed lock) місць на час оплати.

## Розглянуті альтернативи (Alternatives Considered)
* **MongoDB (NoSQL):** Відхилено як основну БД. Хоча вона гнучка та добре масштабується на читання, забезпечення суворих транзакційних гарантій для фінансових операцій та бронювань у ній складніше і менш надійне, ніж у реляційних БД.
* **Тільки PostgreSQL (без Redis):** Відхилено. Прямі запити до БД при напливі користувачів на старті продажів призведуть до перевантаження процесора БД та відмови системи.

## Наслідки (Consequences)
* **Позитивні наслідки:** 100% гарантія відсутності подвійних продажів (завдяки транзакціям PostgreSQL та блокуванням у Redis); висока швидкодія на читання за рахунок кешу.
* **Компроміси (Trade-offs):** Зростає складність інфраструктури (потрібно підтримувати дві різні технології зберігання); необхідно розробити механізм інвалідації кешу Redis при зміні даних у PostgreSQL.
