# ADR-0642: KhNTU Deployment Topology Selection

**Статус:** Прийнято  
**Дата:** 2026-11-26  
**Контекст:** ЛР6 — топологія розгортання стенда Online Ticket Booking & Event Platform після ЛР4–ЛР5.

## Контекст

Після ЛР5 система має Clean Architecture ядро і in-memory Event Bus з двома споживачами всередині процесу API. Потрібно зафіксувати, **де і на чому** це працює в навчальному стенді, і які компроміси прийняті.

## Варіанти

### 1. Один локальний процес Node (без Docker)
- **Плюси:** нуль інфраструктури, `npm start` / `ts-node`.
- **Мінуси:** немає відтворюваного артефакту образу; складно показати edge/TLS і однаковість середовищ.

### 2. Docker Compose: Edge Gateway + один API-контейнер (обрано)
- **Плюси:** одна команда `docker compose up --build`; артефакти (образи, conf) видимі в репо; reverse proxy ізолює TLS; відповідає варіанту А (in-memory EDA всередині API).
- **Мінуси:** один хост — єдина точка відмови; in-memory EventId store не переживає рестарт і не шариться між репліками.

### 3. Compose з RabbitMQ + окремий worker
- **Плюси:** ближче до продакшену, окреме масштабування споживачів.
- **Мінуси:** виходить за межі коду ЛР5 (потрібна заміна транспорту); надлишково для поточного обсягу.

## Рішення

Обираємо **варіант 2**:  
`KhNTU Edge Gateway [nginx-6.42]` + `ticket-booking-api` (образ `ticket-booking/api:1.0`) на одному Docker-хості.  
Клієнт → **HTTPS/TLS1.3 :8443** → gateway → HTTP :8080 → API.  
Події та споживачі — у процесі API (як у ЛР5).

## Наслідки

**Позитивні**
- Стенд описується і (після встановлення Docker) піднімається з репозиторію.
- Діаграма розгортання збігається з `docker-compose.yml`.
- Ядро (Domain/Application) не змінюється.

**Негативні / trade-offs**
- Один хост — NFR доступності 99.9% **не** забезпечується в стенді.
- In-memory шина і `khntu_processed_events_v5`: при `--scale ticket-booking-api=N` ідемпотентність і стан складу **не** коректні між екземплярами → у стенді **1** репліка API.
- TLS на gateway у локальному стенді може бути з self-signed / спрощеним conf; шлях зв’язку на діаграмі лишається HTTPS/TLS1.3 :8443.
- Зовнішні Payment/SMS — заглушки (як у ЛР5), на діаграмі пунктиром.

## Зв’язок з NFR
| NFR | У стенді |
|-----|----------|
| Ізоляція падіння SMS від створення бронювання | Так (споживачі + ідемпотентність у процесі) |
| Тести Domain без БД | Так (ЛР4) |
| Горизонтальне масштабування API | Ні (обмеження in-memory) |
| Availability 99.9% | Ні — один хост |
